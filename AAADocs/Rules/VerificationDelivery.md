# 验证与交付

编译、测试、验收和提交时读本文。

## 负责人自验

- 每完成一个可运行的改动就编译，并跑与改动直接相关的自动化测试或最小复现。尽早暴露错误，不要攒到最后。
- 交付前至少做到：编译通过；原问题能复现的，修复后复现不再出现；新功能走过一次真实入口。
- 视觉问题看实际截图；数值、编译通过、包存在都不能代替可见结果。
- 验不了的（联机、Cook、性能、真实设备等）在回执的"未验证"里写明，不要为了凑完成去降低断言或排除失败场景。

## 统筹集成验证

- 多条工作线都交付后，统筹合并一次，跑一轮集成编译和冒烟。只覆盖这次合并影响到的功能，不重跑历史全量矩阵。
- 集成失败时，交回对应负责人修，修完只重跑失败项。

## 状态写法

- 回执里分清这几种状态：已编译、已测试、已在 UE 里运行、已联机验证。哪一级没做就写没做。
- 证据只留日志或截图路径和一句结论。不写哈希、字节数、身份链或保护记录。
- 失败的日志保留到问题修好为止，之后可以清理。

## 交付

- 交付前按 [CodeConventions](CodeConventions.md) 自审受影响的调用链。
- 需求验收后，一次性同步受影响模块的 Obsidian 笔记，再提交 Git。
- Git：父工程和 Source/GGYGO 子仓分别提交，Obsidian 是独立仓。只 stage 本需求的文件，保留无关的未提交改动。中文 commit 并 push。不自行放开角色／场景素材的忽略范围。
- 需求完成后，把它在看板上的条目改成一行结果，附需求记录和 commit 链接。需求记录里的过程部分删掉，只留结论、接口和仍然有效的约束；过程历史以 Git 为准。
