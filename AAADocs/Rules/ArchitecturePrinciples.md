# 架构与分层

改架构、跨模块协作或决定 C++／蓝图分工时读本文。代码写法见 [CodeConventions](CodeConventions.md)。

## 模块职责

- 修改前确认所属职责、依赖和既有实现。模块间用接口、数据或清晰的直接调用；不读写其它模块内部状态，不新增循环依赖或第二套帧调度。
- 权威状态和执行机制唯一：

| 职责 | 拥有者 |
| --- | --- |
| 选招并请求 GAS | BossAI |
| 能力生命周期及自有资源 | GA |
| 胶囊位移 | CMC |
| 姿态及窗口 | Animation |
| 命中查询与去重 | Combat |
| 伤害结算 | GA／GE／Execution／AttributeSet |

- 快照和派生缓存须有来源、有效期和清理，不与权威状态竞争。

## C++ 与蓝图分层

- **C++**：通用执行原语、蓝图接口与回调、权限、安全校验、命中查询、通用位移／播放、资源申请与释放。通用渲染、Niagara 支撑和音频播放机制也可以在 C++。
- **蓝图及可视化资产**：顶层流程、表现层，以及具体 Boss／角色／招式的阶段条件、选招偏好、连招组合、技能流程、预警／爆发／收尾表现和声音触发。由行为树、Montage、动画曲线、Niagara／材质图和数据资产承载。调整这些业务不应需要重新编译 C++。
- 不把具体对象的业务藏进 C++：不按角色／Boss／招式名称分支，不写固定阶段表、连招表或表现时间线，也不用配置表解释器、"通用化"或蓝图薄壳包装 C++ 的决策。不为迁移业务预建通用脚本解释器。
- 优先"共享蓝图模板＋对象资产配置"。只有资源、参数、连段映射或窗口差异的变体，用子蓝图／CDO／数据资产配置，不复制 EventGraph；新增业务分支、组合或时序时再扩展业务图。判断标准是业务决策在哪里、能否在 UE 里查看和修改，不看图的数量或类名。
- 蓝图只通过 GAS／CMC／Combat 的公开入口消费权威机制，不另建 Tick、位移、伤害或资源生命周期。
- 编辑器 C++／Python 工具只做资产读写、校验和制作，产物必须是 UE 中可查看、可修改的蓝图／行为树等资产。工具不作运行时控制器；制作脚本存在不等于蓝图已经做完。

## 组织与失败处理

- 代码按当前需求的主流程组织。新增分支、状态、抽象或防御须对应实际需求或已确认缺陷。
- 按变化原因、状态所有权和生命周期拆分职责；不按行数切文件，不为小功能过度抽象。
- 修根因，不用特判、猜来源或最小补丁掩盖架构缺陷。
- 必需配置／资产／曲线／接口无效时，明确拒绝、等待真实异步就绪或中止，并给出可定位的诊断；不偷换固定速度、其它动作或成功结果。
- 保留必要的安全检查、幂等释放和引擎合法暂态；显式配置的正常模式不算兜底。
- 已退役的做法：曲线 DA 不恢复；移动失败不能当 Finished。
