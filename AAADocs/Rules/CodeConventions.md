# 代码规范与审核

写代码、审代码时读本文，适用于 C++、蓝图和资产工具。C++／蓝图分工见 [ArchitecturePrinciples](ArchitecturePrinciples.md)，协作与权限见 [TaskWorkflow](TaskWorkflow.md)。

## 代码表达

### 命名与文件

- 类型用 UE 前缀 U／A／F／I／E，布尔量用 b 前缀。
- 名称说明动作、事实、对象或资源阶段。同名谓词实际检查不同事实时，改用对应语义的名称。Original／Expected／Current 等限定词只说明资源关系，不能代替职责名称。
- .cpp 先包含对应头文件，再项目依赖，最后引擎依赖。头文件优先前向声明，.generated.h 放在最后一个 include。
- 运行时代码按 `Source/GGYGO/所属职责/` 组织，头文件和实现可以并列，不建 Public／Private 镜像目录。编辑器专用的宿主和工具放 GGYGOEditor 或明确的测试模块。

### 主流程

- 主流程按业务发生顺序写：请求、准入、执行、提交结果、失败清理。用早返回减少嵌套；真实的异步和回调在边界处说明。
- lambda 用于就近的短计算或真实的回调捕获。连续的业务步骤直接顺序写；复杂、可复用或有独立含义的步骤用具名私有函数或普通 C++ 协作者。拆分时保持捕获寿命、外调顺序、返栈核验和清理责任，不为搬参数建大型上下文。
- 只需组合或纯计算时用普通 C++ 类型；需要反射、引擎组件或蓝图接口才用 UObject。跨调用持有 UObject 时用受 GC 追踪的强引用或弱引用，不用裸指针假定异步寿命。
- 纯计算不持有玩法状态。私有执行资源由原模块拥有，拆分类时不产生第二套 Tick、计时器、Issuer、Ready、Held 或播放归属。

### 状态与接口

- 身份和状态字段在定义处写明来源、写入者、寿命和失效条件。
- 接口直接返回消费者需要的结果及其有效性，不让调用方从诊断文字或遍历记录推断成功、权限或提交值。有消费者的步骤历史、原资源快照和诊断各自保留。改返回结构前核对真实调用方，不丢失清理或后继隔离的依据。
- 比较 UE 反射 Struct 用明确字段或原生值比较。`str`／`repr` 可能含临时实例地址，不能作为相等或变更依据。资产文本里的对象引用按实际对象身份核对。

### 注释

- 文件头用 Doxygen 的 @file、@brief。对外接口写清输入、作用、结果、状态所有者和清理责任，有意义的参数／返回值用 @param／@return。显而易见的私有赋值不逐行注释。
- 用中文写当前契约和原因，UE 术语和标识符保留原文。复杂边界写清会调用谁、可能改变什么、为何保留保护；具体限制写原因，不用成串的 never／no 清单代替契约。
- 不写改动批次、构建次数或版本历史；待退役代码用 TODO 指向实际任务。删分支时同步删掉失效的注释。

## 错误与防御边界

### 失败与结果

- 必需配置或来源失效时拒绝／中止请求并诊断，不以零输出、正常 Finished、固定速度、默认资源或另一能力掩盖。
- 引擎规定的合法暂态、资源退役和幂等清理可以正常无操作，与业务失败分开。显式配置的正常模式不因"禁止兜底"而删除。
- Busy、NotHeld、NotApplicable、Failed 等结果表达不同事实，调用方按契约消费；不能拒绝提交后外层再发布成功。结果枚举只列消费者会分别处理的值，其余原因写进诊断。
- 不用异常／catch 把无效依赖变成功。诊断包含模块、对象／资源和原因，按资源或失败生命周期去重，不每帧刷屏。

### 防御的依据

- 防御须对应真实的输入边界、可变生命周期或已知失效场景，在状态拥有者或入口校验一次；内部沿明确契约消费，不层层判空或全量校验。不为理论风险新增重试、兜底、快照、身份协议或通用框架。
- **外调**指会执行其它代码、可能改变原资源的调用，按实际调用链可达性认定，限于：
  - BP／K2 事件
  - 有外部订阅的委托或广播
  - EndAbility／CancelAbility／EndTask
  - Montage Stop／BlendOut 等引擎回调
  - Actor 或组件销毁
  - RPC／OnRep 接收
  - 确实存在上述行为覆盖实现的虚函数

  是否属于外调以函数实现为准。例如 `ASC::CurrentMontageSetNextSectionName` 只改 Montage 实例数据并复制，不算外调。
- 每处返栈重验须对应上面某一种外调，并在返栈后重取、核验可能改变的原资源身份。
- 同一调用栈内，中间既无外调也没有自有写入改变被验证事实时，复用已验证的输入。保留后置检查的一方要指出会改变该谓词的那次外调或自有写入，指不出就删。不影响后续行为、也不承担诊断的检查删除；承担断言／诊断的写明目的。
- 不建无失效管理的跨帧 Valid 缓存，也不把不同寿命的序号、快照合成一个"当前有效"布尔量。有明确来源、寿命和失效点的预备配置不在此列，例如：授予实例首次准入时按作者配置解析、只缓存成功结果、改配置的一方显式失效、所依赖的弱引用失效即重解析。IsDataValid 仍做完整校验。

### 身份、镜像与计数

- 防 ABA 先用原生寿命：AbilityTask 随 EndAbility 结束，Task 委托随 EndTask 解绑，Timer 在清理时 Clear。只有回调可能越过拥有者寿命时才签发身份；一个寿命一个身份，同一拥有者同一寿命的多个 serial／token 合并。
- 消费者可以持有自己的订阅 handle、原资源快照和清理凭据。判断镜像是否冗余，比较事实、寿命、消费者和释放义务：同事实同寿命的副本合并；原终止快照与后继活动资源不能因值相同而混用。名字相似不等于可以合并，名字不同也不等于应该并存。
- 跨模块缺口由拥有者修复；写权不够时协调换手，不在消费方复制拥有者职责。
- 64 位单调计数不做耗尽判断。上网络或序列化的窄字段（如 int32 修订号、16 位请求号）按实际宽度处理环绕。
- 线程检查只覆盖真实线程入口。静态配置在加载／IsDataValid 或已有失效点校验，执行时只核仍可能改变的输入，不另建"已校验"标志。

## 复杂度审核

### 何时做

- 完整需求交付前集中做一次，深度与风险相称，优先找正确性问题、职责混杂、重复机制和无依据的防御。小修改只查受影响的调用链，不反复做全项目审计，不以格式偏好或假设风险阻塞交付。
- 新增长期状态／缓存／身份协议、修改回调生命周期或迁移旧接口时，实现前先核对相关边界。并在现有任务条目里写明：原生／Lyra／既有机制是什么、具体的需求或失效序列及依据、本次的最小增量。只写"异步""ABA"不算理由。
- 行数、分支数、lambda 数量和测试体积只用来找热点，不作为拆文件或删测试的指标。没找到 C++ 调用不等于反射／蓝图／序列化没有使用。

### 六项必查

| 审核项 | 要回答的问题 | 整改方向 |
| --- | --- | --- |
| 职责与依赖 | 哪些变化原因混在一起？请求、执行、表现各是谁？主调用链能否读出正常、失败和清理路径？有没有新增循环依赖？ | 主函数按业务顺序写；按输入／输出、生命周期与所有权拆分，保留原权威入口 |
| 状态与提交 | 每项事实谁拥有？是否多处写同一个完成／失败转换，或拒绝后仍发布成功？ | 唯一提交、明确结果；只读快照保留来源和有效期 |
| 防御依据 | 检查防什么失效？此处有无外调／返栈／网络边界？中间写入是否改变谓词？结果有何用途？ | 保留真实边界的保护；合并同次纯路径的重复验证，删无效的尾部检查 |
| 迁移残留 | 新旧链是否同时运行？旧 API 谁还在用？有无恒失败分支或未迁移的派生发布？ | 同一需求内接回调用方并退役旧入口；兼容入口写明消费者和删除条件；不直接删反射字段 |
| 业务与扩展 | 具体对象逻辑是否真的在蓝图／资产里？是否只挪了数值而 C++ 仍在决定业务？是否预建了第二套协议？ | C++ 只留通用机制和蓝图接口；只实现真实需求 |
| 测试与构建 | 生产、测试、编辑器宿主分清了吗？是否只为夹具保留第二条生产写链？断言是否锁死旧内部实现？外部 API 夹具依据来自实际绑定还是实现推断？ | 测试走真实入口；先保留等价外部契约覆盖再迁移内部断言；保留原失败证据 |

测试相关的补充：

- UE Python 调用以实际 ScriptName／绑定名为准，在真实 Editor 用反射元数据或 hasattr 核实一次；夹具只模拟已核实的名字，不从 C++ 类名推导。
- "后继资源不被旧栈清除""原输入不串入后继请求"属于外部契约。内部 serial／receipt／phase 断言可以随设计迁移，但不能因字段退役就删掉它保护的外部结果。

### 结论与留痕

- 每个重要问题归为：必要保留、可合并、可拆分、可退役、待验证、需用户决策。
- 在现有模块任务或[修复清单](../Coordination/Module_Audit_Repair_Ledger.md)里简述：代码／调用链依据与根因（事实与推测分开）；推荐的职责／状态归属、受影响的调用方和清理责任；实际实现、验证结果和未验证边界。
- 不为单个判空、函数或内部步骤新增 JSON、全项目哈希、交接报告或 Canvas。相同事实引用原记录，不多处抄写。

### 整改与验收要点

- 先关真实遗漏、错误的成功结果和迁移残留，再合并重复规则、拆分独立职责。拆分后的每部分要能说清输入、输出、依赖、状态所有者和清理责任；只搬代码、改名或减行数不算完成。
- 不改变已确认语义的技术整改直接做。玩法／输入／镜头政策、实质兼容、反射或资产丢失风险、引擎源码修改交用户决定。
- 作者自审和统筹验收检查：主流程可读性、依赖、状态／执行唯一、失败传播、清理路径、新增机制的必要性与最小增量、旧 API 的退役或兼容条件。范围、哈希核对和编译不能代替设计审核。

### 不以瘦身为名做的改动

- 删除真正外调后的身份保护、引擎规定的暂态或合法末帧贡献。
- 把网络输入证明、请求序列、执行准入和播放身份强行合成一个状态。
- 删测试或失败证据来缩减数字；为测试保留没有生产需要的旧状态写链。
- 因为没有 C++ 引用就删 UFUNCTION、UPROPERTY、UCLASS 或既有资产。
- 用泛用事件总线、统一状态机、守护管理器或另一个帧调度器解决局部复杂度。

### 应主动退役的模式

在受影响调用链里遇到就收敛，不留待以后整理：

- 每个订阅点重复的注册／注销样板：收到资源拥有者的一处注册与释放。
- 只转发参数的原生入口包装，或同一入口仅默认参数不同的多个重载。
- 事后扫描兜底：用定期扫描或终止后遍历补漏，代替在拥有者处清理。
- 主流程里的测试钩子和测试日志：测试应经真实入口断言外部结果。
- 没有实际消费者的兼容分支。
- 写着任务阶段、批次或计划的注释。
