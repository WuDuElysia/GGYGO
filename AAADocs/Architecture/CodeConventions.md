# GGYGO 代码规范与复杂度审核机制

适用于项目 C++、蓝图及资产工具。项目协作权限、写入交接和用户决策以 [AGENTS.md](../../AGENTS.md) 为准；本文规定代码表达与审核方法，不引入另一套审批、帧调度或状态管理机制。

## 代码表达

- 类型采用 UE 前缀 U／A／F／I／E，布尔量用 b 前缀；接口、变量和文件名使用清楚的职责名称。
- 主流程按业务发生顺序组织，让读者沿主要调用链看清请求、准入、执行、结果提交与失败清理。用必要的早返回减少嵌套，避免把连续步骤藏在多层闭包、转发或历史结果回捞中；真实异步与回调流程在对应边界说明。
- 名称说明动作、事实、对象或资源阶段。同名谓词若实际检查不同事实，应采用对应语义的名称；Original／Expected／Current 等限定词用于说明必要的资源关系，不能代替职责名称。身份与状态字段在定义处说明来源、写入者、寿命和失效条件，不要求阅读散落的检查才能理解。
- lambda 适合就近的短计算或真实回调捕获；连续业务步骤优先直接顺序表达。复杂、复用或具有独立含义的步骤可用具名私有函数或普通 C++ 协作者；不机械把所有 lambda 改成函数，也不为搬运参数建立大型上下文。拆分时保持捕获寿命、外调顺序、必要返栈核验与清理责任。
- 接口明确给出消费者真正需要的结果及其有效性，避免由诊断文字或遍历过程记录猜测成功、当前权限或提交值。确有消费者的步骤历史、原资源快照与诊断保留各自用途；修改返回结构前核对真实调用方，不因表达简化丢失清理或后继隔离依据。
- 文件头用 Doxygen 的 @file、@brief 说明当前功能。对外接口写清输入、作用、结果、状态所有者及必要的清理责任；有意义的参数／返回值使用 @param／@return。不为显而易见的私有赋值逐行补注释。
- 项目注释用中文描述当前契约和必要原因，UE 术语与标识符保留原文。复杂边界说明会调用谁、可能改变什么及为何保留保护；具体限制写清原因，不用成串的 never／no 清单代替契约。不写改动批次、构建次数或版本历史；待退役代码可用 TODO 指向实际任务。删除分支时同步清理不再成立的注释。
- .cpp 首先包含对应头文件，其次项目依赖，最后引擎依赖；头文件优先前向声明，反射头的 .generated.h 保持最后一个 include。
- 当前运行时按 Source/GGYGO/所属职责/ 组织，头文件与实现可并列；不要求建立 Public／Private 镜像目录。仅编辑器使用的宿主与工具进入 GGYGOEditor 或明确的测试模块。
- 仅需组合或纯计算的职责优先使用普通 C++ 类型；确需反射、引擎组件或蓝图接口才使用 UObject。跨调用持有 UObject 时明确采用受 GC 追踪的强引用或弱引用，不靠裸指针假定异步生命周期。
- 纯计算不持有当前玩法状态；私有执行资源由原模块拥有，不因拆分类而建立第二套 Tick、计时器、Issuer、Ready、Held 或播放归属。
- C++ 承担稳定机制与权限／生命周期；常改的角色差异、招式组合、时序窗口、曲线和表现参数放在蓝图、Montage 或配置资产，不硬编码具体角色。

## 错误、暂态与防御边界

- 必需配置或来源失效，应明确拒绝／中止对应请求并诊断，不以零输出、正常 Finished、固定速度、默认资源或另一能力掩盖失败。
- 引擎规定的合法暂态、资源退役和幂等清理可正常无操作；与业务失败区分。已显式配置的正常模式不因“禁止兜底”而被误删。
- Busy、NotHeld、NotApplicable、Failed 等结果表达不同事实，调用方必须按契约消费；不能先拒绝提交，再由外层发布成功结果。
- 不使用异常／catch 把无效依赖转为成功。诊断包含模块、对象／资源和原因，按资源或失败生命周期抑制重复，不无限每帧刷屏。
- 外调按实际调用链可达性判断：虚函数、委托／广播、BP事件、销毁或网络接收可能执行其它代码并改变原资源；引擎函数也可能有这类回调。针对实际可能改变的身份，在返栈后重取并核验原资源；无外调的同栈段能否复用检查结果，还须核对中间写入与后续谓词依赖。
- 核验结果不影响后续行为、也不承担必要诊断时，应去除无效检查。若承担断言／诊断，明确其目的；不把所有函数尾部检查一律视为冗余。
- 同次调用栈内，中间既无外调、也未改变被验证事实时，可复用已验证输入。自有状态写入可能改变后续谓词结果，应按实际依赖保留必要检查；“无外调”不单独证明后置检查冗余。不能为减少检查建立未经失效管理的跨帧 Valid 缓存，或把不同生命周期的序号、快照合成一个“当前有效”布尔量。
- 单一权威允许消费者持有自己的订阅 handle、原资源快照和清理凭据。判断镜像是否冗余须比较事实、寿命、消费者与释放义务；同一事实及寿命的副本应收敛，原终止快照与后继活动资源不能因值相同而混用。跨模块缺口由拥有者修复，写权不足时协调换手，不在消费方复制拥有者职责。
- 计数耗尽、线程断言及配置校验说明实际边界与用途，不以理论风险批量新增，也不机械全删。线程检查覆盖真实线程入口；静态配置在加载／IsDataValid或已有失效点校验，执行时只核仍可能改变的输入，不重复全量验证，不另建校验缓存。

## 复杂度审核机制

### 触发与范围

在完整需求交付前执行一次；新增长期状态／缓存／身份协议、修改回调生命周期、迁移旧接口或出现明显职责混杂时，在实现前先核对相关边界。小修改只检查受影响调用链，不每次重新全项目审计。

新增持久状态、身份或协议及修改重要生命周期边界时，在现有任务条目说明原生／Lyra或既有机制、具体需求／失效序列及代码或原失败依据，以及本次最小增量。不能只用“异步”“ABA”或“严格要求”解释新增机制；不新增逐方法审批或独立报告。

行数、分支数、lambda 数量和测试体积只用于发现热点，不作为强制拆文件、改写回调、删除测试或完成百分比。审核覆盖实际调用方、状态写入点、失败与清理路径；未发现 C++ 调用不等于反射／蓝图／序列化使用不存在。

### 六项必查

| 审核项 | 必须回答的问题 | 常见整改方向 |
| --- | --- | --- |
| 职责与依赖 | 哪些变化原因混在一起？谁请求、执行、表现？主要调用链能否清楚读出正常路径、失败与清理？是否新增循环依赖？ | 主函数按业务顺序表达，命名说明事实与阶段；按输入／输出、生命周期与所有权拆分，保留原权威入口 |
| 状态与提交 | 谁拥有每项事实？是否多处写同一完成／失败转换，或拒绝后仍发布成功？ | 唯一提交与明确结果；只读快照保留真实来源和有效期 |
| 防御依据 | 检查防止什么失效？此处是否有外调／返栈／网络边界？中间写入是否改变谓词依赖？结果有何用途？ | 保留真实边界保护及状态改变后的必要检查；合并同次纯路径重复验证，删除无效尾部检查 |
| 迁移残留 | 新旧链是否同时运行？旧 API 谁仍使用？是否有恒失败分支或未迁移的派生发布？ | 在同一需求内接回必要行为与调用方并退役旧入口；必要兼容入口写明实际消费者与删除条件，不直接删反射字段 |
| 业务与扩展 | 是否把角色业务写进通用机制？是否为无实际接入场景维护第二套协议？ | 配置／组合／扩展点；只实现真实需求，不预建通用框架 |
| 测试与构建 | 哪些是生产、测试、编辑器宿主？是否只为夹具保留第二条生产写链？断言是否锁死旧内部实现？外部 API（UE Python／蓝图反射名、命令行参数、日志格式）的夹具依据来自实际绑定还是实现推断？ | 测试适配真实入口，隔离环境宿主；先保留等价外部契约覆盖，再迁移内部实现断言，保全原失败证据。UE Python 调用以实际 ScriptName／绑定名为准，在真实 Editor 通过反射元数据或 hasattr 核实一次；夹具只模拟已核实的名字，不从被测实现或 C++ 类名推导 API |

不同 serial、Origin／Input／Prepared、活动资源／原生末次贡献不凭名字相似就合并。先说明各自的事实、寿命和消费者，再决定是否重复。

后继资源不被旧栈清除、原输入不串入后继请求等可观察结果属于外部契约，ABA测试可能验证这些结果。内部serial／receipt／phase断言可随设计迁移，但不能只因字段退役就删除它所保护的外部结果。

### 审核结论与留痕

每个重要问题归入：**必要保留、可合并、可拆分、可退役、待验证、需用户决策**。在现有模块任务或[修复清单](../Coordination/Module_Audit_Repair_Ledger.md)中简述：

- 具体代码／调用链依据与根因；确认事实和风险推测分开。
- 推荐职责／状态归属、影响的生产调用方与清理责任。
- 实际实现、编译／必要冒烟结果及未验证边界。

不为每个判空、函数或内部步骤新增 JSON、全项目哈希、重复交接报告或 Canvas。新问题只有构建／失败复现／机器消费确需时才追加机器证据；相同事实引用原记录，不多份抄写。

### 执行与验收

1. 组长先检索现有实现，独立制定职责内方案与步骤；跨模块需求指定牵头，相关组长共同收敛接口。统筹确认文件唯一写入者与公共窗口，不逐方法代拟设计。
2. 优先关闭真实遗漏、错误成功结果及迁移残留，再合并重复规则和拆分独立职责。拆分后的每部分须能说明输入、输出、依赖、状态所有者和清理责任，主要调用链应更容易理解；仅搬代码段落、改名或减少行数不算职责重构完成。
3. 不改变已确认语义的技术整改直接实施。玩法／输入／镜头政策、实质兼容性、反射或资产丢失风险、引擎源码修改仍交用户决定；只有相关工作线等待。
4. 同文件始终一个写入者；接口与原写入者冻结后交接。所有 C++ 写入者冻结，再按完整可运行链安排批量编译与必要冒烟。
5. 保留原问题的最小严格复现／原断言，验证受影响生产链；不扩历史全量矩阵，不降低断言或排除失败场景制造成功。静态检查与离线夹具只证明脚本自身一致，不证明外部 API 存在；真实反射查询与 PIE／Editor 运行分别标明证据层级，前者不代后者。未测联机、Cook、视觉、性能分别明示，不以普通冒烟代替。
6. 作者自审与统筹验收同时检查主流程可读性、依赖、状态／执行唯一、失败传播、清理路径、新增机制的基线缺口与最小增量、旧 API 的退役或兼容条件。可读性核对在现有受影响调用链和交付审核内完成，不新增逐步报告；范围／哈希核对和编译不能代替必要性与设计审核，已覆盖条款仍须按实际调用链落实。
7. 完整需求开发和约定测试完成后，集中同步模块 Markdown／Canvas、进度及中文 Git 交付；实现中只保留协作必需状态，不逐步骤改笔记。

### 不以瘦身名义进行的改动

- 不删除真正外调后的身份保护、引擎规定的暂态或合法末帧贡献。
- 不将网络输入证明、请求序列、执行准入与播放身份强行合成一个状态。
- 不删测试／失败证据来缩减数字，不为测试继续保留无生产需要的旧状态写链。
- 不凭无 C++ 引用直接删除 UFUNCTION、UPROPERTY、UCLASS 或既有资产。
- 不新增泛用事件总线、统一全模块状态机、守护管理器或另一个帧调度器来解决局部复杂度。
