# 代码注释规范

## 核心原则：注释描述当下，不记录变迁

注释的读者是"第一次看这段代码的人"，他需要知道**这段代码现在是什么、为什么这样写**。
他不需要知道它以前是什么样、什么时候被改的、由哪个任务改的。

变更历史属于 git log 和提交信息，不属于源码。写进注释会有三个后果：
代码越改注释越长；历史描述会随时间失去参照（被提及的旧类已经不存在了）；
读者要先理解一段不存在的代码才能理解现在的代码。

## 禁止写进注释的内容

- 与旧实现的对比：「旧实现是 X，现在改成 Y」「取代了 `FOldClass`」「原本在 A，现在在 B」
- 变更动作的记录：「删掉了」「不再」「改为」「迁移而来」「新增的」
- 项目时间线标记：「阶段 5」「阶段 6 补齐」「Phase 7」「待重构」
- 已删除的类型、文件、字段的名字（读者查不到它们）

## 应该写进注释的内容

- 这段代码做什么，以及**为什么用这个做法而不是显而易见的另一个做法**
- 约束与前提：调用时机要求、线程要求、谁负责调用、幂等性
- 陷阱：改动这里会破坏什么、为什么某个看起来多余的判断不能删
- 数值的来源与含义：单位、坐标系、轴序约定
- 网络语义：哪些状态需要复制、哪些参与预测、不一致会导致什么

## 表达尚未完成的功能

功能确实没做完时，陈述**当下的事实与后果**，不要写计划时间线。

```cpp
// 不好：阶段 6 会接入曲线采样，当前恒为默认值
// 好：  曲线采样尚未接入，本字段恒为 None，转身状态不会被进入
```

后者让读者知道现在会发生什么，且不会因为计划调整而失效。

## 允许的外部参照

与 Lyra 等**当前存在的**参考工程做对比是允许的，因为读者可以真的去看那份代码。
但要写成设计依据（「Lyra 把 ASC 挂 PlayerState，本项目挂角色自己，因为一名玩家带三个角色」），
而不是变更记录。

## 语言

注释用中文。标识符、API 名、Unreal 固定术语保持原文。
