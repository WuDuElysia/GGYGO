                                                    wr# 用户偏好

## 语言

- 与用户交流、解释、提问、汇报进度以及编写面向用户的文档时，全程使用中文。
- 代码中的标识符、API 名称、类名、函数名和 Unreal Engine 固定术语保持其原文；必要时用中文解释。

## 动画层归属

- 当前动画层是新版 ZZZ 动画层：`UZZZAnimInstance` + ZZZ AnimBP，源码位于 `Source/GGYGO/Animation/zzzAnim/`；其中按职责包含 `Data/`、`Capture/`、`Locomotion/` 三个子目录，顶层保留动画实例与日志文件。
- `Source/GGYGO` 模块没有 `Public/`、`Private/` 划分，头文件与 `.cpp` 按职责子目录并列，`ModuleDirectory` 是唯一 include 根。

## 参考工程

- Lyra 参考工程完整副本在 `F:\ue_project\LyraStarterGame`，只读。需要参照 Lyra 的结构或实现时，直接检索该路径的实际源码，详细目录索引见 steering `lyra-reference`。

## Spec 命名

- 所有针对 ZZZ 动画层的 spec，功能名必须以 `zzz-` 前缀开头（例如 `zzz-moving-walkrun-gait`
- 非动画层的 spec（例如逻辑管线 `intent-pipeline`）不加 `zzz-` 前缀。
## 自主执行

- 默认一路做到任务完成，不要中途停下来征求同意。技术细节（目录布局、命名、.gitignore 规则、依赖放 Public 还是 Private、提交如何拆分、第三方产物是否纳入版本控制等）自行判断并执行，做完在汇报里说明决定和理由即可。
- 只有两种情况才停下来问：一是会破坏或丢失现有工作且不可恢复的操作（删除大量文件、强制回滚、重写历史、改动生产环境）；二是需求本身有歧义、按任一种理解做都可能整体返工。
- 不要把"这个可选，你要不要"作为收尾。有倾向就直接落地，把备选方案作为汇报里的一句提示，让用户事后可以推翻。
- 遇到过程中发现的新问题（漏掉的目录、体积过大的资产、错误的路径），先按最合理的方案处理掉，再在汇报中说明。

## 解释与图表要带伪代码

- 用户是程序员，看得懂代码逻辑，但不想为了理解一个机制去翻源码 —— 翻代码会打断开发节奏。
- 所以解释机制、写架构图节点、写文档时，**用简洁伪代码代替散文描述控制流**。
  伪代码要点：保留关键函数名与调用顺序、保留判断条件与早退，省掉类型声明、
  空指针检查、日志、`Super::` 之类的样板。
- 伪代码之后紧跟"为什么这样写"和"改了会坏什么"，那部分才用散文。
- 不要贴整段源码，也不要只写抽象描述（"每帧求值并混合"这种说了等于没说）。
  目标是读者看完伪代码就能在脑子里跑一遍流程。

## Git 提交

- 每完成一个需求就提交一次，不要把多个需求堆在一个提交里。提交前先 `git status --short` 核对改动范围，只 add 本次需求实际涉及的文件。
- 当前只有 `Source/GGYGO` 是 git 仓库，工程根 `f:\ue_project\GGYGO` 没有初始化仓库。因此 `GGYGO.uproject`、`Plugins/`、`Config/`、`Content/`、`.kiro/` 的改动不在版本控制内，提交时要在汇报中说明哪些改动没能纳入提交。
- 提交信息用中文，一行概述 + 必要的要点列表。

## 任务执行与静态检查复盘

- 执行长检索必须拆成短检查组，并在每组开始前向用户报告范围，在返回后立即报告结果；不能长时间静默等待。
- 不能只相信 tasks.md 的完成状态；每个任务完成后必须核对实际文件存在性、关键内容和引用，状态与工作区不一致时必须停止后续任务。
- 发现已完成任务的关键产物缺失时，必须暂停在当前检查点，先恢复产物并重新静态核对，再继续后续任务。
- 子代理调用返回 `aborted` 时不得声称任务已完成；必须读取实际文件状态，确认是否有部分产出。
- 阶段一静态检查结论在本地编译前只能写“静态检查通过，编译待本地验证”，不能写“编译通过”。
- 关于代码的搜索、引用核对和符号检索，统一只搜索 `Source/GGYGO/**`；`.kiro/specs` 仅用于读取任务/设计/需求文档，不纳入代码搜索范围。
