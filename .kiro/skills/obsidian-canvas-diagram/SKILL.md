# Obsidian Canvas 制图规范

## 适用范围

本 skill 用于维护 `F:\Obsidian\Doc\lyra学习笔记\GGYGO架构规划\` 下的模块化架构笔记与 Canvas。根目录保留导航、跨模块关系和实施状态；AbilitySystem、Camera、BossAI 等模块各有自己的目录。目标是让读者能沿着结构文档、结构图和流程图回答：

- 这个模块或步骤负责什么？
- 它依赖谁、输出什么？
- 为什么这样设计？
- 出问题时先查哪里？
- 当前哪些部分已经验证，哪些仍是缺口？

## 开始前：先读取上下文

1. 先读 [[计划蓝图]] 找到模块目录；读取同目录的 `结构.md`、结构图、流程图和需要修改的子图。修改已有图时确认节点、边、布局和颜色。
2. 再读对应 `计划_*.md`、[[模块参考]] 和直接相邻模块的结构文档，确认现状与目标的边界。
3. 需要添加代码类名、路径或当前状态时，优先核对 `Source/GGYGO/**` 的实际内容；不要把推测写成事实。
4. 修改现有图时保留已有节点 ID、边 ID 和可复用布局，除非确实需要重排。

## Canvas 数据格式

`.canvas` 是 JSON，不是 Markdown。默认使用当前图中已有的 `text` 节点和边：

```json
{
  "nodes": [
    {
      "id": "unique-node-id",
      "type": "text",
      "text": "Markdown 内容",
      "x": 0,
      "y": 0,
      "width": 420,
      "height": 260,
      "color": "4"
    }
  ],
  "edges": [
    {
      "id": "unique-edge-id",
      "fromNode": "source-node-id",
      "fromSide": "right",
      "toNode": "target-node-id",
      "toSide": "left",
      "label": "实际传递的语义"
    }
  ]
}
```

必须满足：

- 文件始终是合法 JSON；不要留下注释、尾逗号或 Markdown 外壳。
- 所有节点和边的 ID 全局唯一；边的 `fromNode`、`toNode` 必须指向现有节点。
- 节点正文使用 Markdown；代码标识符、API 名、类名、函数名和 Unreal 固定术语保持原文。
- 默认不混用多种节点类型；现有 GGYGO 图以文本节点为主，除非用户明确要求文件节点、链接节点或分组节点。
- 边必须有清楚的 `label`，描述真实的依赖、数据、事件或控制流，不写空泛的“相关”。
- 节点尺寸要能容纳正文，避免文字被截断；相邻节点不能重叠。

## 模块交付形态

每个被规划的模块在自己的目录同时拥有：

- `结构.md`：说明模块职责、当前核心类/数据、跨模块关键接口的参数或输入、作用与输出、持有/调用/继承关系、当前实现与目标设计的边界；不抄完整头文件。Camera 至少讲清 `CameraComponent → CameraModeStack → CameraMode → CameraModeView`，以及 HeroComponent / GA 如何影响有效模式。
- `GGYGO_结构_*.canvas`：用类或职责节点画静态关系。边标签明确写“持有”“继承”“调用接口”“发布数据”等；每个关键接口在节点里写“接口名 → 作用”，必要时写输入/输出或生命周期。只列对本模块或跨模块协作有意义的接口。跨模块节点写接缝并链接到对方模块的 `结构.md`。
- 主流程 Canvas：按引擎实际时序画事件、接口调用、状态改变和分支。每个关键节点至少说明触发者、实际调用的接口及其产物；边标签写调用/数据/结果，不用「处理」「更新」代替接口链。若一步仍有多段关键决策、回滚或跨模块执行，拆成同目录的流程子图，主图保留接口入口和链接。静态类清单与字段结构回到结构图和 `结构.md`。
- 关键实现说明：会影响时序、预测、状态恢复或可见画面的算法，写在同目录 Markdown 并在相关流程子图画出关键分支。例如 CameraStack 的实例复用、入栈贡献与混合顺序；动画曲线的来源标记、基线重置、差分、消费与目标拆环。主图保留入口，不把这些机制压成一句“更新”。
- 原有 `计划_*.md`：保留设计理由、算法细节、待实现方案与验收；不要把计划画成已实现事实。

目录与文件命名以 [[计划蓝图]] 的索引为准。新增模块先补齐结构 Markdown 和结构图，再为有运行链路的模块建主流程图。概念过多、边交叉过密或一个节点写成整段源码时，应按可独立理解的子问题拆图，而不是继续增大节点。

## 图的类型与内容结构

### 架构总览图

用少量大节点表达系统边界。建议包含：

1. 文字文档入口：说明“为什么这样设计”和“现在有什么”。
2. 已确认的架构决策：写硬约束和关键取舍。
3. 各模块节点：标题、职责、关键取舍、风险或缺口，并链接到模块子图。
4. 验证状态：区分已经跑通、尚未验证和已知但无关的问题。
5. 图之间的导航节点：用 `[[文件名.canvas|显示文本]]` 连接相关图。

### 模块依赖图

- 明确声明：`A → B` 表示 A 依赖 B。
- 无依赖或公共词汇表放在较基础的位置；依赖范围最大的编排层放在后面。
- 模块节点写实际目录、代表类、职责和边界。
- 只画有架构意义的依赖；不要把每个 include 或偶然调用都画成边。
- 在图中突出跨层铁律，例如状态唯一入口、表现层只读、移动权威归 CMC 等，但这些内容必须来自当前设计笔记或代码。

### 模块结构图

- 表达“谁拥有谁、谁调用谁的哪个关键接口、哪个类提供数据、结果由谁消费”；箭头方向和边标签一起读，不用无语义的“相关”。
- 以类、接口、资产或清晰的职责组为节点，不把一整套运行时步骤装在类节点里。
- 当前实现与计划中的类分开；计划节点显式标“目标/未实现”。若一个模块自身也需要分层，拆独立结构子图。
- 结构图对应同目录 `结构.md`；节点至少写关键接口的输入/作用/输出或副作用，边写调用方与被调方、传递内容。Markdown 补充完整契约与设计依据，但不能代替图内的必要接口说明。
- 简洁指删掉无关接口，不是把关键接口只剩函数名；读者沿图应能回答调用方给了什么、谁持有状态、返回或发布了什么。

### 运行链路图

按实际执行顺序排布，通常从左到右或从上到下。节点写「谁触发 → 调用哪个真实接口（重要参数）→ 状态或返回结果」，而非只写业务动词；实现细节在 `计划_*.md` 或子图中。每个跨模块跳转至少出现一次具体接口名；计划接口若尚不存在必须标「目标/未实现」，不要伪装成源码。需要表现分支时，分开主路径、失败路径、重试路径和反馈路径，边标签说明分支条件。不要把多个不同生命周期语义压缩成一个“完成”节点。

### 流程子图

每张子图只展开一个可命名的问题，例如“能力组仲裁”“相机覆盖恢复”“Boss 换形态事务”。入口说明所属主流程，出口回到主流程或下游子图；计划中的路径标目标状态。类接口关系交给结构图。

## 颜色和布局

颜色数字是现有图的语义标记，不要把它当作装饰。新增节点先寻找同类节点并复用同类颜色；现有图中常见倾向如下，遇到冲突时以目标图的既有用法为准：

- `6`：标题、阅读指引、排查或说明性节点；
- `4`：基础设施、输入、系统和低依赖模块；
- `5`：核心模块、主流程、状态处理或重要设计节点；
- `3`：辅助说明、分支、重试和顶层补充节点；
- `1`：事件、表现、结果或确认类节点。

布局规则：

- 标题和阅读说明放在图的入口处；
- 线性执行链保持单向排列，避免边反复穿过节点；
- 分支放在主路径旁边，回流边标明“重试”“结束后回调”等语义；
- 模块图按层级或依赖方向聚类；
- 需要跨图展开的内容放在独立子图，不把一个节点塞成整篇笔记；
- 新增节点的坐标、宽高应参考相邻节点，保持同一张图的视觉节奏。

## 链接规则

- 链接文字笔记使用 Obsidian wikilink，例如 `[[模块参考]]`、`[[计划蓝图]]`、`[[Camera/结构|Camera 结构]]`。
- 链接 Canvas 使用 `[[GGYGO_结构_AbilitySystem.canvas|结构图]]`、`[[GGYGO_流程_AbilitySystem.canvas|流程图]]` 这类带显示文本的链接。
- 链接必须指向实际存在或本次同时创建的文件；不要写无法解析的占位路径。
- 根导航页同时列结构 Markdown、结构图、主流程图和子图入口；每张图的入口节点提供返回结构文档和相关主图的链接。

## 内容表达规则

- 先写当前事实，再写原因、约束和后果；不要把变更历史写进图中。
- 代码事实使用实际类名、函数名、Gameplay Tag 和资产路径；不把伪代码冒充已实现代码。
- 未完成内容要明确写当前后果，例如“Boss 换形态事务未实现，当前只能维持单形态 Avatar”，不要只写“后续实现”。
- 设计选择要说明取舍，例如为什么状态走 GAS、为什么移动由 CMC 权威、为什么需要中转层。
- 结构图列接口名而不复制头文件；流程图只保留关键调用，不在每步嵌入代码块。读者需要细节时走 Markdown 链接。
- 关键实现若有容易误解的代码级约束，核对当前 `.h/.cpp` 再写。例如栈的索引方向、动画曲线第一帧是否只建基线，不能仅凭旧图复述。
- 问题排查节点使用“现象 → 优先检查项”的表格，避免只列文件名而不说明症状。

## 修改后的检查

完成后按顺序核对：

1. 用 JSON 解析器确认 `.canvas` 是合法 JSON。
2. 检查节点 ID、边 ID 是否重复，边是否引用存在的节点。
3. 检查所有新增 wikilink 的目标文件是否存在；移动文件后检查仓库内旧链接、Canvas 文件节点路径和同名 `结构.md` 的歧义。
4. 检查每条边是否有准确标签，方向是否符合图开头声明的规则。
5. 检查新节点是否与同类节点使用一致的颜色、标题层级、宽高和 Markdown 结构。
6. 对照源码检查：结构图每个关键类的接口输入、职责、输出与调用方；流程图每个关键步骤的真实接口与分支；关键算法、资产名和“已验证/缺口”描述。不存在的目标接口必须显式标注。
7. 重新读取保存后的文件，确认内容没有被截断、转义破坏或意外覆盖。

汇报时简要说明：修改了哪张图、增加了哪些节点/边、使用了哪些跨图链接，以及 JSON 和引用核对结果。
