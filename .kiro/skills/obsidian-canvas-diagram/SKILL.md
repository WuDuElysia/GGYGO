# Obsidian Canvas 制图规范

## 适用范围

本 skill 用于维护 `f:\Obsidian\Doc\lyra学习笔记\GGYGO架构规划\` 下的架构 Canvas。目标不是单纯摆放方框，而是让读者能沿着图回答：

- 这个模块或步骤负责什么？
- 它依赖谁、输出什么？
- 为什么这样设计？
- 出问题时先查哪里？
- 当前哪些部分已经验证，哪些仍是缺口？

## 开始前：先读取上下文

1. 先读取目标 `.canvas` 文件，确认当前节点、边、布局和颜色，不要凭空重画。
2. 同时读取它链接的文字笔记和相邻子图，尤其是 `计划蓝图`、`模块参考` 以及对应模块的 `.canvas`。
3. 需要添加代码类名、路径或当前状态时，优先核对 `Source/GGYGO/**` 的实际内容；不要把推测写成事实。
4. 修改现有图时保留已有节点 ID、边 ID 和可复用布局，除非确实需要重排。

## Canvas 数据格式

`.canvas` 是 JSON，不是 Markdown。默认使用当前图中已有的 `text` 节点和边：

```json
{
  "nodes": [
    {
      "id": "unique-node-id",
      "type": "text",
      "text": "Markdown 内容",
      "x": 0,
      "y": 0,
      "width": 420,
      "height": 260,
      "color": "4"
    }
  ],
  "edges": [
    {
      "id": "unique-edge-id",
      "fromNode": "source-node-id",
      "fromSide": "right",
      "toNode": "target-node-id",
      "toSide": "left",
      "label": "实际传递的语义"
    }
  ]
}
```

必须满足：

- 文件始终是合法 JSON；不要留下注释、尾逗号或 Markdown 外壳。
- 所有节点和边的 ID 全局唯一；边的 `fromNode`、`toNode` 必须指向现有节点。
- 节点正文使用 Markdown；代码标识符、API 名、类名、函数名和 Unreal 固定术语保持原文。
- 默认不混用多种节点类型；现有 GGYGO 图以文本节点为主，除非用户明确要求文件节点、链接节点或分组节点。
- 边必须有清楚的 `label`，描述真实的依赖、数据、事件或控制流，不写空泛的“相关”。
- 节点尺寸要能容纳正文，避免文字被截断；相邻节点不能重叠。

## 图的类型与内容结构

### 架构总览图

用少量大节点表达系统边界。建议包含：

1. 文字文档入口：说明“为什么这样设计”和“现在有什么”。
2. 已确认的架构决策：写硬约束和关键取舍。
3. 各模块节点：标题、职责、关键取舍、风险或缺口，并链接到模块子图。
4. 验证状态：区分已经跑通、尚未验证和已知但无关的问题。
5. 图之间的导航节点：用 `[[文件名.canvas|显示文本]]` 连接相关图。

### 模块依赖图

- 明确声明：`A → B` 表示 A 依赖 B。
- 无依赖或公共词汇表放在较基础的位置；依赖范围最大的编排层放在后面。
- 模块节点写实际目录、代表类、职责和边界。
- 只画有架构意义的依赖；不要把每个 include 或偶然调用都画成边。
- 在图中突出跨层铁律，例如状态唯一入口、表现层只读、移动权威归 CMC 等，但这些内容必须来自当前设计笔记或代码。

### 运行链路图

按实际执行顺序排布，通常从左到右或从上到下。每个步骤建议采用：

````markdown
### N　步骤名称

```text
伪代码或关键调用链
```

为什么这样做、它解决什么问题。

约束、容易出错的地方，以及出现什么现象时应检查哪里。
````

需要表现分支时，把主路径、失败路径、重试路径和反馈路径分开，并让边标签说明分支条件。不要把多个不同生命周期语义压缩成一个“完成”节点。

### 模块子图

每个子图至少说明：

- 模块职责；
- 输入、输出和依赖；
- 关键类或数据资产；
- 关键设计取舍及其原因；
- 当前缺口、待配置项和验证状态；
- 返回总览图或相关模块图的链接。

## 颜色和布局

颜色数字是现有图的语义标记，不要把它当作装饰。新增节点先寻找同类节点并复用同类颜色；现有图中常见倾向如下，遇到冲突时以目标图的既有用法为准：

- `6`：标题、阅读指引、排查或说明性节点；
- `4`：基础设施、输入、系统和低依赖模块；
- `5`：核心模块、主流程、状态处理或重要设计节点；
- `3`：辅助说明、分支、重试和顶层补充节点；
- `1`：事件、表现、结果或确认类节点。

布局规则：

- 标题和阅读说明放在图的入口处；
- 线性执行链保持单向排列，避免边反复穿过节点；
- 分支放在主路径旁边，回流边标明“重试”“结束后回调”等语义；
- 模块图按层级或依赖方向聚类；
- 需要跨图展开的内容放在独立子图，不把一个节点塞成整篇笔记；
- 新增节点的坐标、宽高应参考相邻节点，保持同一张图的视觉节奏。

## 链接规则

- 链接文字笔记使用 Obsidian wikilink，例如 `[[模块参考]]`、`[[计划蓝图]]`。
- 链接 Canvas 使用 `[[GGYGO_模块_AbilitySystem.canvas|▸ 打开子图]]` 这类带显示文本的链接。
- 链接必须指向实际存在或本次同时创建的文件；不要写无法解析的占位路径。
- 入口节点提供阅读顺序；子图提供回到总览或相关图的路径。

## 内容表达规则

- 先写当前事实，再写原因、约束和后果；不要把变更历史写进图中。
- 代码事实使用实际类名、函数名、Gameplay Tag 和资产路径；不把伪代码冒充已实现代码。
- 未完成内容要明确写当前后果，例如“具体攻击 GA 仍为空壳，战斗链路尚未跑通”，不要只写“后续实现”。
- 设计选择要说明取舍，例如为什么状态走 GAS、为什么移动由 CMC 权威、为什么需要中转层。
- 伪代码只保留能帮助理解链路的关键调用，不复制整段源码。
- 问题排查节点使用“现象 → 优先检查项”的表格，避免只列文件名而不说明症状。

## 修改后的检查

完成后按顺序核对：

1. 用 JSON 解析器确认 `.canvas` 是合法 JSON。
2. 检查节点 ID、边 ID 是否重复，边是否引用存在的节点。
3. 检查所有新增 wikilink 的目标文件是否存在。
4. 检查每条边是否有准确标签，方向是否符合图开头声明的规则。
5. 检查新节点是否与同类节点使用一致的颜色、标题层级、宽高和 Markdown 结构。
6. 检查图中的代码类名、路径、资产名和“已验证/缺口”描述是否与当前源码和笔记一致。
7. 重新读取保存后的文件，确认内容没有被截断、转义破坏或意外覆盖。

汇报时简要说明：修改了哪张图、增加了哪些节点/边、使用了哪些跨图链接，以及 JSON 和引用核对结果。
